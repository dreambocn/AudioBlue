# AudioBule 全面代码审查报告

审查日期：2026-10-25。

本轮覆盖 Core、主窗口、共享设备行、托盘快速面板、设置与语言、桌面集成、音频会话标识、日志与脱敏导出、打包脚本及 CI。审查开始时工作区干净；没有修改业务实现，没有连接或断开真实蓝牙设备，没有修改用户启动项或执行安装卸载。

## 结论与证据等级

发现 8 项可定位的问题：2 项 P1、4 项 P2、2 项 P3。最应优先修复的是异步事件的对象生命周期，以及刷新后界面状态与底层连接脱节。

- **定向模拟验证**：链接本轮构建的真实 Core 静态库，使用独立模拟 Provider，验证枚举失败丢失连接状态、迟到关闭通知覆盖重连状态、退订后已复制回调继续执行。
- **静态确认**：依据可达调用路径与具体代码确认其余缺陷；涉及 WinRT 真实事件时序的部分没有在物理蓝牙设备上触发。
- **运行限制**：本轮原生冒烟未通过托盘初始化入口，未取得完整窗口交互和视觉验收结果。下文 UI 结论来自代码审查，不声称完成读屏、高 DPI 或真实桌面交互验收。

## R1 · P1 · 在途事件回调可在对象析构后访问裸指针

位置：`AudioBule.Core\ConnectionManager.cpp:13-24`、`AudioBule.Core\SimpleEvent.h:35-62`、`AudioBule.Core\WinRtDeviceProvider.cpp:182-194`。

`ConnectionManager` 使用捕获裸 `this` 的回调订阅 `ConnectionLost`。析构只等待自己创建的连接/断开线程，然后调用 `Remove`；它没有等待 Provider 触发的外部回调。`SimpleEvent::Raise` 先复制处理器再解锁执行，`Remove` 无法撤销已经复制的处理器。因此可发生：系统关闭事件复制回调 → Manager 退订并析构 → 回调继续执行 `HandleConnectionLost`，访问已经释放的对象和互斥锁。

Provider 自己的 `StateChanged` 回调同样捕获裸 `this`，并且没有保存事件令牌，析构时无法主动退订和协调在途回调。这是同一条生命周期问题的另一个入口。

影响：退出、设备掉线和后台连接事件交错时可能发生访问已释放内存、崩溃或死锁。

证据：定向程序输出 `copied_callback_calls_after_remove=1`，证明退订不具有等待在途回调完成的语义。程序使用安全计数器验证这一前提，没有主动执行非法内存访问，也没有声称已经复现真实崩溃。[微软事件生命周期文档](https://learn.microsoft.com/en-us/windows/apps/develop/cpp-winrt/handle-events)也明确说明，异步事件即使已经退订，仍可能到达开始析构的对象。

建议：将 Provider 和 Manager 的外部回调接入独立的共享生命周期状态，保存并撤销 WinRT 事件令牌，关闭入口后等待已经进入的回调退出，或者使用能安全提升所有权的弱引用机制。仅增加析构时退订或一个未与执行协调的原子布尔值，不能完整解决该竞争。增加带门闩的并发销毁回归测试；当前 `DestructionWaitsForInFlightWork` 用例在销毁前已经 `.get()` 等待结束，没有覆盖这个场景。

## R2 · P1 · 刷新失败会丢失仍然存在的底层连接

位置：`AudioBule.Core\ConnectionManager.cpp:93-128`、`AudioBule.App\App.xaml.cpp:243-250`。

枚举异常被捕获后直接 `devices.clear()`，随后用空的 `updated` 覆盖 `m_entries`。当连接中的设备因为枚举异常或枚举缺项而被移除时，刷新路径没有调用 Provider 关闭现有会话。Provider 的 `m_connections` 与 Manager 的快照由此分离。再次枚举到同一设备时，又会创建默认的“未连接”条目。

此外，`Refresh` 吞掉异常且返回 `void`，App 的 `succeeded` 仍为 `true`，所以界面不会显示 `RefreshFailed`，而是显示“还没有可连接的设备”。退出保存的 `ConnectedDeviceIds` 也会遗漏仍存在的会话。

定向模拟结果：

```text
before_refresh_connected=1
enumeration_failure_reported_to_caller=0 entries_after_failure=0 provider_live=1 disconnect_calls=0
reappeared_state=0 connected_ids=0 provider_live=1
```

其中 `state=0` 为 `Disconnected`。这验证的是本轮真实 Manager 与模拟 Provider 的不一致，不代表主动操作过用户设备。

建议：区分枚举失败与成功空列表；失败保留最近有效快照，并返回可用于界面提示的错误结果。成功枚举后移除仍有会话的设备时，在锁外完成关闭或显式保留连接记录。[微软蓝牙音频示例](https://learn.microsoft.com/en-us/windows/apps/develop/media-playback/enable-remote-audio-playback)也在设备移除时释放对应连接资源。

## R3 · P2 · 旧连接的关闭通知能够移除同设备的新连接

位置：`AudioBule.Core\WinRtDeviceProvider.cpp:183-193`、`AudioBule.Core\ConnectionManager.cpp:390-418`。

`StateChanged` 回调只捕获设备 ID。检测到其发送者关闭后，直接 `m_connections.erase(id)` 并发出 `ConnectionLost(id)`，没有比较当前表项是否仍为该发送者，也没有连接代次标识。如果旧连接的异步通知在该设备重新连接后到达，就会删除新连接的表项，并将 Manager 的新状态改为未连接。

定向模拟在完成断开与重连之后注入上一代的延迟关闭通知，得到 `after_stale_close_state=0 provider_new_connection_live=1`，确认 Manager 无法区分通知代次。生产 Provider 的实际事件乱序尚未用真实蓝牙设备触发；该模拟不能替代驱动层复现。

建议：每次连接分配代次标识，处理关闭事件时同时验证设备 ID、当前发送者/代次；只有该回调确实移除了当前连接时才发出丢失通知。增加断开后重连与旧回调迟到的回归场景。

## R4 · P2 · 连接状态订阅晚于 Open，存在漏掉关闭事件的窗口

位置：`AudioBule.Core\WinRtDeviceProvider.cpp:140-144`、`:179-198`。

当前在 `StartAsync`、`OpenAsync` 均完成后才注册 `StateChanged`。如果 `OpenAsync` 返回成功后、订阅前连接已经被系统关闭，这一次关闭通知就无法被当前处理器收到。注册后也没有再次检查 `connection.State()`，代码仍返回连接成功，Manager 和主窗口/托盘都可能停留在“已连接”。

证据等级：静态时序缺口已确认；本轮没有用物理设备触发该窗口。

建议：在开始异步操作前安装状态监听，并用受保护的连接记录协调连接完成与关闭事件；订阅后及公布成功前检查当前状态，避免用一次历史的 Open 成功结果覆盖已关闭状态。[微软示例](https://learn.microsoft.com/en-us/windows/apps/develop/media-playback/enable-remote-audio-playback)也先注册状态事件，再开始连接启用流程。

## R5 · P2 · 首次托盘登记失败后，现有重试机制会被立即销毁

位置：`AudioBule.App\App.xaml.cpp:102-105`、`AudioBule.App\TrayIconService.cpp:80-89`、`:110-116`。

`AddIcon` 失败时设置一秒重试定时器，但初始化随即发布 `m_ready=true`、`m_started=false`。`WaitUntilReady` 立即返回 `false`，App 随即 `m_tray.reset()`，销毁线程、消息窗口和定时器。登录阶段 Explorer 尚未准备好、Shell 临时拒绝登记等可恢复情况，也会变成本次会话永久无托盘。

影响：`--startup` 会因无托盘回退为显示主窗口，关闭/最小化行为也会走无托盘分支；预期的恢复逻辑不能发挥作用。

建议：区分“线程/窗口初始化失败”与“Shell 图标暂未登记”；后者保留服务与重试，异步向主窗口报告托盘可用性变化。增加首次登记失败、随后重试成功的故障注入验证。本轮冒烟失败发生在托盘入口，但尚未证明它就是本项可恢复时序造成，不能将两者等同。

## R6 · P2 · 设备筛选的选中状态没有暴露给辅助技术

位置：`AudioBule.App\MainWindow.xaml:40-41`、`AudioBule.App\MainWindow.xaml.cpp:307-310`。

“全部设备”和“已连接设备”使用普通 `Button`。点击后只更新两个装饰矩形的可见性，没有原生选择或切换状态，也没有其他可访问状态属性。界面视觉上有下划线表示当前筛选，UI Automation 却只能取得两个普通按钮，无法通过选择/切换语义确定当前筛选。

建议：改用适合互斥筛选的原生选择控件，或实现正确暴露选择状态的控件及自动化对等体，并测试键盘焦点、选中状态和读屏反馈。本轮是静态语义审查，没有完成 Narrator 验收。

## R7 · P3 · 诊断导出成功也会显示为红色错误提示

位置：`AudioBule.App\MainWindow.xaml:29`、`AudioBule.App\MainWindow.xaml.cpp:357-358`、`AudioBule.App\App.xaml.cpp:153-162`。

共用 `StatusBar` 的严重性固定为 `Error`，`SetStatusKey` 仅修改文字并打开提示。导出成功的 `DiagnosticsExportSuccess` 和部分成功的 `DiagnosticsExportPartial` 也经过同一方法，最终用错误颜色和图标呈现成功信息。

建议：状态接口显式携带严重性，成功使用成功级别、部分导出使用警告级别，失败使用错误级别；两种语言共用语义，不依靠资源键名称临时猜测。

## R8 · P3 · 保存设备列表只去除相邻重复项

位置：`AudioBule.Core\Settings.cpp:27-38`、`tests\Settings.test.cpp:197-207`。

`std::unique` 只删除相邻重复项，当前没有先排序或维护已见集合。输入 `A, B, A` 会原样保留，`A, 空值, A` 也会在随后删除空值后留下重复项。去重发生在 32 条限制之前，异常配置还可能让重复设备挤掉有效设备。当前测试只覆盖 `A, A, 空值, B`，无法捕捉非相邻重复。

证据等级：由实际算法和现有测试输入静态确认；本轮文件写入测试受环境限制，没有宣称完成保存后读回复现。

建议：保持原始顺序，用已见集合一次性过滤空值与重复项，再限制设备数量；补充非相邻重复、空值隔开的重复及数量边界用例。

## 其他风险与覆盖缺口

以下记录为待进一步验证的风险，不计入上述 8 项已定位问题：

- **退出等待没有总时限**：`App.xaml.cpp:314-324` 先移除托盘，再等待刷新/启动项和 `WaitForIdle`；`WinRtDeviceProvider.cpp:140-144` 阻塞等待异步系统调用，`CancelConnection` 只撤销界面请求。如果驱动请求迟迟不返回，退出可能长期停留且托盘已移除。需要以可控制阻塞的 Provider 验证退出策略，并明确产品是否提供等待/强制结束选择；不能仅凭静态代码断言正常设备必然挂死。
- **刷新错误与蓝牙不可用的说明不足**：目前支持性检查主要判断 API 类型存在，不能据此说明蓝牙硬件或无线电当前可用。资源中的 `OfflineTitle` / `OfflineBody` 尚未接入状态呈现。建议在解决 R2 时明确区分枚举失败、蓝牙不可用与有效空列表。
- **持续集成 UI 覆盖不足**：CI 执行双架构核心测试和安装验证，但未传入安装脚本的 `-RunAppSmoke`，默认只检查主窗口标题。语言、主题、托盘菜单、键盘焦点和诊断导出流程没有在当前 CI 中获得完整原生冒烟覆盖。
- **历史实现残留**：`TrayMenuBuilder.cpp` 仍编译进 App，但当前生产托盘已经使用 `QuickPanel`，没有找到 `ShowTrayMenu` 调用。该文件中的旧菜单和“开机自启尚未启用”文字不能代表当前功能，后续可清理以降低误维护风险。
