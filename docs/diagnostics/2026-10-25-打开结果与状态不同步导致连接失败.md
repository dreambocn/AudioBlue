# 打开结果与原生状态不同步导致连接失败

日期：2026-10-25。以下时间为北京时间。

## 结论

已复现并修复一个会直接导致当前 `0x800704D4` 失败的应用时序问题：Windows 的 `OpenAsync` 返回 Success 后，`AudioPlaybackConnection.State` 可能短暂仍为 Closed，随后才更新为 Opened。原先 Provider 在成功返回后立即检查 `IsOpen()`，把这段状态同步间隙当作连接中止，主动清理本来即将建立的连接。

该检查是在此前审查修复中为防止关闭后的假成功而加入的，缺少对成功结果与状态属性不同步的处理。本轮不据此解释所有更早的蓝牙故障或首次无声问题；当前这条失败路径已得到原生探针和正式安装版实测支持。

## 证据链

1. 22:14:37 自动连接及 22:17:11—22:17:29 多次手动重试，均记录 Open 阶段失败、`0x800704D4`。刷新正常，蓝牙和音频服务正常。
2. 独立原生探针枚举并创建同一部手机的连接，记录 Start 完成时 State=0；Open 返回 Status=0、ExtendedError=0，同时 State 仍为 0；随后收到 State=1 的事件，500 毫秒快照仍为 1。探针正常释放测试连接。
3. 手机 ADB 的 A2DP 状态机记录 22:29:07.534 已连接，协商 SBC、44100 Hz、16 bit、立体声；22:29:08 探针清理时断开，证明这轮真实建链与编码协商可以成功。
4. 安装修复版后，22:40:00.495 记录 `provider.state_synchronized` 成功，State 从 0 到 1，等待耗时 16 毫秒；同一操作随后记录 `connection.completed` 成功。
5. 正式安装版界面显示手机已连接；22:40:41 的手机 ADB 快照为 `STATE_CONNECTED`、`mActiveDevice` 指向电脑、`mIsPlaying=false`。手机没有播放也能保持连接，不以零峰值判断失败。

Windows 原生枚举 Closed=0、Opened=1；应用自身状态枚举 Connected=2。两者不能混用。

## 修复

- `WinRtDeviceProvider` 仅在 SDK 已返回成功、但状态尚未打开时，短时间重复读取只读 `IsOpen()`，最长等待 2 秒。该过程在连接工作线程上进行，不阻塞 XAML 界面，不重新调用 Open，不检测音频是否在播放。
- 真正的关闭事件、记录移除或替换仍立即终止状态同步；超时保持失败并清理，不把关闭会话当成功。
- 增加 `provider.state_synchronized` 事件，保存状态前后值及等待毫秒数；后续可以区分 SDK 原始打开失败与成功后的状态同步失败。
- 复用模拟会话，增加“SDK 成功但 Opened 延迟到达”和“等待状态时真实关闭”两项回归；持续关闭无事件的既有回归使用短等待预算。
