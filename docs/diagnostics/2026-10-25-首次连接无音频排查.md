# 首次连接已连接但无音频：排查记录

日期：2026-10-25。时间线均为北京时间（UTC+8）。

## 判断

本次现象已经与本机日志对应：第一次点击后调用返回成功、界面显示已连接，但没有声音；用户在 AudioBule 中断开再连接后恢复。

**证据最符合首次 A2DP 媒体链路协商或音频流初始化未正常完成。这个判断仍是原因方向，而不是已经定位到某个 Windows/Realtek 驱动函数的确定根因。** 现有运行日志没有保存第一次的底层原生连接状态、静音值和音频峰值，尚不能完全区分：

1. 底层打开后迅速关闭，旧实现漏掉事件，界面保留成功状态。
2. 底层仍是 Opened，但 Windows/手机之间的媒体流或路由没有正常启动；第二次重建会话后恢复。

不能仅凭其他项目的同类报告就将本机问题确定为驱动缺陷，也不能将应用显示“已连接”解释为已经验证音频正在流入。

## 代码核查

- `AudioBule.Core\WinRtDeviceProvider.cpp` 的适配器按顺序等待 `StartAsync().get()` 和 `OpenAsync().get()`。没有发现漏调用 Open 或未等待 Start 的问题。
- 原实现和修正版都会保存连接对象，不能将问题简单解释为函数返回就释放了会话。
- 修正版的 `IsOpen()` 检查原生 `AudioPlaybackConnectionState::Opened`，同时安装关闭监听并处理代次，能防止部分过期成功状态。但原生 Opened 本身没有“已经收到非静音音频”的语义。
- `ConnectionManager.cpp` 的 `stateAfter=2` 是应用自己的 `ConnectionState::Connected`，不是 Windows 原生枚举值。原生枚举只有 Closed=0、Opened=1。
- `AudioSessionIdentity.cpp` 仅修改会话名称/图标，不设置音量、静音和输出路由，也不搬运音频数据。它有贯穿应用运行的 MTA 工作线程；当前没有证据支持“连接线程结束导致整个 MTA 消失”这一解释。
- 原有 spike 文档中 `State=1(Connecting)` 的说法是枚举映射错误，本轮已勘误，避免继续据此误判连接阶段。

微软文档说明：[StartAsync](https://learn.microsoft.com/en-us/uwp/api/windows.media.audio.audioplaybackconnection.startasync) 用于启用接收，[OpenAsync](https://learn.microsoft.com/en-us/uwp/api/windows.media.audio.audioplaybackconnection.openasync) 用于尝试连接；[原生状态枚举](https://learn.microsoft.com/en-us/uwp/api/windows.media.audio.audioplaybackconnectionstate) 不包含播放或实际收流状态。

## 外部旁证及边界

另一个同 API 项目的维护者记录了“显示已连接但无声、断开重连恢复”的同类报告：[AudioPlaybackConnector2 issue 1](https://github.com/N0ahTM/AudioPlaybackConnector2/issues/1)。Windows 11 兼容分支也列出了首次手动连接可能无声的限制：[AudioPlaybackConnector-Win11](https://github.com/summerwind6/AudioPlaybackConnector-Win11#known-limitation)。

这些是项目维护者的一手症状报告，支持本问题可能位于共有的 A2DP 初始化路径；它们不是微软对本机驱动根因的确认。该分支提到的自动重连设置条件也不能直接套用到本机，因为本机当前自动重连设置为开启。


不应以固定睡眠或检测零峰值后无条件自动重连作为已经证实的修复：暂停、静音和静音片段也会出现零峰值，盲目重连会打断正常会话。
